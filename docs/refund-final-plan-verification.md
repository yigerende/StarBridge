# 代退最后一轮套餐核验与收尾

2026-11-28 用户授权修复、推送 GitHub 并更新正式。此前单笔人工处置已完成，本次不重放或补扣历史单。

## 问题与行为

原来 `fallback_cycles == max_cycles` 后，最后一次导出停用异常直接自动结束并释放费用，未再次核验个人套餐。资源任务进入 review，只查询成员是否仍在，导致同账号后续申请一直排队。

- 重办轮数仅限制重新邀请办理，最后一次提交仍进入现有移出、登录、等待、个人套餐核验。沿用原每轮核验次数、间隔及代理绑定。
- 新增持久化 `refund_execution.fallback_final`。最终核验可确认 Free 成功或确认仍付费失败，不能重新邀请、登录提交或通过管理操作确认拒绝后再次提交。新字段默认 false，不修改历史进度和配置。
- Free 按原规则完成，只结算一次；最终仍付费失败并释放冻结，只记录实际套餐结果，不伪造上游受理。清理事实与终态在原钱包/订单事务内保存。失败资源进入 watching，成员、邀请、席位与观察期仍由原维护流程确认。
- 核验失败达到原次数上限时，使用已有 attention 状态，费用保留冻结、不扣费。已持久确认移出才释放物理母号；该账号由未完成执行继续全站防重。未确认移出不能释放母号。
- 人工继续核验复用已有 verify_only 操作、原订单、原凭据与最新绑定；最终核验标志不因次数重置、配置修改或重启丢失。既有上游特定状态只读核验约束保持。
- 两端订单列表/详情、办理总览及用户 API 按已授权当前页批量读取阻塞原因。查询失败、上一单结果待核实、上一单清理中分别提示，不暴露其他客户、母号、代理、凭据或上游原文；状态与费用事实不投影伪造。新增目标邮箱索引。

## 范围

正常成功流程不增加请求或等待；原 runtime、refundworker、订阅与注册执行核心保持不变。用户 API 原路径、参数、状态集合、幂等及字段类型保持，文档2.9.3补充已有 queued/attention 含义。仅异常核验耗尽从提前失败释放改成明确待核实，避免误报与重复办理。
