# 代退手机验证客户提示

代退子号登录明确返回 `phone_verification_skipped` 时，运营时间线有原因，客户此前只能看到通用失败提示。本次统一在客户订单列表、详情、办理总览和用户 API 显示手机验证原因，运营查询沿用同一说明。

## 显示规则

- 已失败且费用已释放：说明“上游要求手机验证，本次登录未完成”，提示先在官方登录页面完成验证，再重新提交；零服务费单明确无需服务费。
- 仍处理、核实或待跟进，或费用未释放：说明原因，提示联系客服处理原单，暂勿重复提交；不声称已退款或释放。
- 只使用最新一次主办理登录已提交的结构化失败，排除异步协议跟踪、此前登录失败、后续已取得团队会话、已提交/受理及成功订单。不把手机验证误写成邮箱码、密码错误或网络问题。

在鉴权后的读取响应补充说明，不改历史订单、事件、钱包、登录重试、代理或原核心。按本页 ID 单次批量查询；正常成功、排队、取消等无需额外查询，内部登录事件有专用索引。异步路由在工作线程读取，办理执行没有新增网络或数据库步骤。

## 用户 API

请求、状态枚举、HTTP 状态、幂等与费用字段保持。复用 `order.message` 和列表 `items[].message`；已有可选字符串 `error_code` 增加 `phone_verification_required`，不伪造上游 HTTP 状态。只有最终通用失败事件的响应文本替换，存储历史不变。`/api/v1/activity` 保持既有字段。用户文档 2.9.2，操作总数仍为 30。

## 验证

隔离 PostgreSQL 13 项回归通过，包括私有 Go 桥与网页/用户 API/管理员 API、跨用户拒绝、费用未释放、零费用、新登录重试、异步旧诊断、成功/提交屏蔽、快照变更及只读数据核对。500 单一次批量查询，20 并发/40 批读取通过；既有总览 3000 单/50 并发100查询和代退50并发提交、24并发取消回归通过，没有真实上游调用。

前端类型检查和生产构建、原执行核心来源校验通过；1440/390 浏览器验证列表与详情提示。发布从 GitHub 预构建，经新镜像隔离验收、三业务空闲检查及备份后切换；正式结果记入生产 runbook，不重放旧单。
