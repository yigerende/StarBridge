# 星桥订阅付款核实与取消续费恢复

2026-11-10。本次只修改 StarBridge，Space 和旧 xufupython 不变。用户要求本地修复合并后，由主会话推送 GitHub 并发布星桥；本侧会话没有推送或更新正式环境。

## 正式故障证据

- 订单 `9160863cc0a79f859306d1553bc7063a`：已确认付款、订阅生效；取消接口返回 404，正文是 `no active subscription found for account`，前后查询均显示续费开启。旧逻辑把这个业务响应归为普通 http_404，没有后续自动恢复。上下游状态不一致已确认，具体上游原因不能仅凭客户端日志确定。
- 订单 `23ec11c204e599e949845f1a9d02594c`：付款成功；取消请求超时，随后三次状态查询均超时。已有 GET 网络重试确实执行过，但耗尽后没有持久恢复。Space 对该订单仍识别付款成功。
- 订单 `529798dc9b6c7f28d30c56b194cb7354`：confirm 遇到 proxy_connect，随后五次付款查询均返回 400。数据库从未记录此单付款成功，实际是未识别，不是成功状态被回退。事后只读重查原 checkout 返回 `checkout_not_active_session`；原五次日志未保存错误正文，不能断言每次都是相同正文。用户独立核实已付款开通，客户端现有记录不足以独立证明上游扣款事实。
- 三笔均属于 Space merge。第三笔后来已有人工停止、授权推送和合并操作，本修复不恢复这些历史任务、不修改历史订单、不补扣服务费。

## 新行为

适用于 `gener_direct_pay` 和 `cslive_go_direct_pay`。独立 `cslive_full_go`、原注册引擎核心和代退核心不在本次修改范围。

1. 提交 confirm 前，在同一事务中保存付款防重标记和加密的原 checkout / PaymentIntent 引用。保存失败不能越过提交边界。不会保存完整银行卡或 CVC 到恢复上下文。
2. confirm 409、超时或非 JSON 后继续核实；若错误正文自身带有与原交易一致的成功证据，也保留该证据。HTTP 失败不会直接解释为未付款。
3. 查询原 checkout，持有原 PaymentIntent 的 client secret 时查询该 intent。原 checkout 明确关闭时，读取同一 checkout 的 init 状态；该请求不含卡、付款方式、confirm 或创建新 checkout。只有明确 paid / succeeded 才结算；关闭、complete/unpaid、既有会员资格都不能代替付款证据。不同 checkout、intent、币种拒绝结算。
4. 同步查询仍未知时保持订单 processing、API payment.state=checking，继续有限次数的持久核实。次数沿用 `payment.network_restart_limit`，间隔沿用 `scheduler.retry_delay_seconds`；每轮只核实一次原交易，不重新提链/付款。设为 0 则不追加后台核实。
5. 成功后用现有行锁结算一次，继续原 Go 收尾。取消接口仅上述精确业务 404 进入延后恢复；普通404、403不因此变成可重试。网络错误/限流/指定5xx等仍按原 GET 重试策略，耗尽后由持久队列在配置间隔恢复收尾。
6. 续费查询或取消遇到401，即使此前主动刷新过，也调用原 session 接口刷新并保存，再查状态。取消累计最多两次写请求的原有上限保留，重启不清零；恢复先查状态，已关闭不再取消。
7. 付款后重试次数/间隔沿用 `renewal_check_limit` / `renewal_check_interval_seconds`。两阶段均受 `subscription_wait_seconds` 和原代理有效期限制；付款核实也受原凭据有效期限制。不会更换订单代理。网络错误后关闭失效空闲连接，保留Cookie和路由。
8. 仍无法确认付款时才进入 review，并保留冻结服务费。明确拒付才释放。已确认付款成功不会因订阅/取消失败回滚成未付款。

## 持久化与发布

- 新增 `subscription_recoveries` 表，无历史回填。完成后清空加密核实上下文；只有本版本新提交的两类订单自动登记。
- 原执行和恢复共享每单数据库锁1886015，防止活跃提交与恢复竞争；进程退出后锁自动释放，5秒后可接续。付款、收尾各自持久状态不会靠内存重试维持。
- 付款开关、调度暂停和部署维护均阻止领取恢复任务；管理员删除、代理切换和更新器空闲检查识别新执行锁。原冻结/结算账本及取消写入防重检查保留。
- 发布需构建新 Python 应用和 `go-post-payment` 二进制，并正常执行幂等 schema 初始化。保留正式数据库、`.env`、注册运行目录及密钥。不得将本地测试库搬到正式，也不得为发布手动重试这三笔订单。
- 没有真实上游付款、取消或负载测试。上游仍不给明确交易证据、session 已不可刷新或代理过期时，系统仍需人工核实；不能承诺仅凭关闭的 checkout 一定恢复成功。
