# 订阅登录态连续性（2026-11-17）

用户要求先修复付款前重试沿用旧登录态的问题，随后追加核对完整订阅流程中的全部刷新位置。验证完成后用户明确授权推送 GitHub 并更新正式环境；按预构建、在途空闲检查、备份和更新后验收流程发布，不重放历史订单。正式完成状态见生产 runbook。

## 问题与修复

当前 `cslive_go_direct_pay` 提链的 Refresh 原先只更新 Go 进程内存。刷新成功后遇到提链 HTTP 400，下一轮重新领取订单仍使用最初提交的 `subscription_runs.credentials_enc`。付款后首次执行虽重新读库，也可能因此拿到旧凭据。

新增私有 stdin/stdout 凭据确认协议：每次付款前刷新成功且身份匹配后，Go 发出 AT、登录 Cookie、SessionToken 的快照；Python 校验账号、邮箱、Cookie 完整性及当前订单轮次，在原字段加密保存并提交事务后才 ACK。没有保存成功就停止本次提链。异常响应及身份不符不覆盖最后成功的凭据。

保存同时更新本轮 Python 内存，付款审批使用新 AT。本单登录态统一以 `subscription_runs.credentials_enc` 为准：付款前开始执行时重新读取；付款后首次执行及恢复都重新读取，并覆盖收尾快照中的凭据。Go 恢复只从快照恢复执行进度，AT/Session/Cookie 使用订单当前值，不从旧快照恢复。数据库行锁、执行轮次、原密文比较以及付款提交/付款成功边界，阻止旧进程覆盖新凭据。保留原凭据保留期限、账单、价格、推广码、代理和资金状态，不增加数据库字段。

付款后共用 Go 模块所有刷新入口统一调用“刷新并保存”方法，包括首次、401 恢复、取消续费前和独立 refresh 操作；保存 ACK 完成前不能发下一步请求。补齐 Cookie 单段/分片替换、删除处理以及 SessionToken 同步；付款回跳响应的 Cookie 变化也保存后继续。已刷新凭据优先于更早的提链请求 Cookie 快照。刷新返回其它账号/邮箱时恢复原登录 Cookie，避免把不匹配状态写入收尾进度。

## 实际刷新与读取顺序

| 位置 | 使用的登录态 | 成功后的保存点 |
| --- | --- | --- |
| 付款前首轮刷新 | 领取时从数据库解密的本单凭据 | 新增凭据 ACK，提交事务后继续 |
| 付款前账号查询 401 后刷新 | 本轮最近成功刷新后的 AT/Cookie | 同一凭据 ACK |
| 提链 400 或原单网络重试 | 重新领取时读数据库，包含前轮已保存新值 | 每次成功刷新继续覆盖本单版本 |
| 同轮付款审批 | 回调已更新的 Python 本轮凭据 | 不发起新的刷新 |
| 付款后首次刷新 | 重新读取本单 `credentials_enc` 创建收尾进度 | 原 `subscription_followups` 与 `subscription_runs` 同事务保存 |
| 付款回跳 | 上一步刷新后的登录态 | 响应 Cookie 有变化时保存 |
| 套餐核实 401 后刷新 | 当前 Go 收尾状态 | 保存确认后再次查询套餐 |
| 取消续费前主动刷新 | 套餐核实后的当前状态 | 保存后查询续费状态 |
| 续费查询/取消返回 401 后刷新 | 当前状态 | 保存后先核实续费状态，保留原防重规则 |
| 付款后刷新内部重试 | 当前内存 Cookie；保留上次响应合法轮换的 Cookie | 原成功刷新保存点；最终异常由原收尾进度保存路径处理 |
| 中断恢复 | 两段都重新读订单凭据；收尾快照只恢复进度，不能覆盖订单最新登录态 | 继续原保存协议 |

每阶段不重新查询数据库。一次执行内共用当前内存状态，关键刷新成功后持久化；新一轮或中断恢复才重新装载。刷新请求用 Cookie 获取 AT，不能仅替换 AT 而保留旧登录 Cookie。

首次刷新时机、提链 400 重试次数/间隔、原网络换代理、已提交付款只核实、成功结算与失败释放规则保持。独立取消续费、原注册和代退引擎不属于本轮改动范围。共享付款后模块的改动覆盖其订阅调用方。
