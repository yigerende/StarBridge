# 订阅提链异步诊断

2026-11-17：用户要求补齐提链与 Session 刷新诊断，异步保存，不拖慢用户办理，并推送 GitHub、更新正式。

## 范围

仅补 `cslive_go_direct_pay` 所用 Go create-checkout 的可观测性。没有改变上游请求顺序、参数、次数、刷新判断、原单重试、付款防重或资金结算；没有实施此前讨论的刷新凭据持久化，也不重跑历史订单。原注册引擎、代退核心、用户 API 与界面不变。

原日志仅有整个提链调用的 `http_400` / `session_expired`。Python 捕获但未保留 Go stderr，无法还原失败子步骤。本次新增仅供内部接入使用的 `--diagnostics-json`，与返回业务结果的 stdout 分离。

## 留存内容

- 本地订单号及 trace round；HTTP 子步骤类别、方法、状态、耗时、网络阶段耗时、已知上游错误码。
- Session 刷新是否拿到 AT、是否返回 error、已知刷新错误（例如 `RefreshAccessTokenError`）、返回账号是否存在/一致。
- 轮次初始、刷新前后的 AT / SessionToken / 登录 Cookie 版本指纹及变化布尔值。指纹用主密钥派生的逐订单 HMAC，无法还原凭据；不同订单不能交叉关联。
- Cookie 版本只比较两个实际登录 Cookie 家族及其分片，忽略设备 Cookie 和排列顺序。
- 未知错误值仅记 `other` / `redacted_error`，不保存任意响应文字、请求正文、完整响应、URL、邮箱、AT、Session、Cookie、代理地址或卡片资料。Go 与 Python 分别执行字段和类型白名单过滤。

## 性能与边界

Go 每次只在内存收集最多 192 条事件，超限保留前 96 条与最新 96 条；正常退出时输出一份有界诊断帧，无额外上游请求或写盘。Python 业务线程只截取至多 256 KiB 并 `put_nowait`，后台单线程解析、二次过滤、写入轮转文件；64 份队列最多约 16 MiB 原始帧。诊断不占用数据库连接。

队列满则丢弃新增诊断，后续记录携带丢弃数；写入失败计数并继续，不同步补写、不改变订单结果。关闭应用时最多等待 2 秒排空。突然断电、强杀应用或 Go 尚未输出诊断帧即被杀死时，可能丢失未落盘诊断；原事务中的订单状态、资金和付款防重记录保持原机制。

默认目录为 `$MAINTENANCE_DIR/diagnostics/checkout.jsonl`，正式对应 `/opt/1panel/apps/starbridge/.maintenance/diagnostics/checkout.jsonl`。目录 0700、文件 0600；每份约 10 MiB，保留当前及 4 份历史，更新容器后仍保留。仅服务器运维读取，不增加网页或用户 API 出口。

维护根目录保持 root:root/0755；宿主更新器安装及启动时单独创建 diagnostics 子目录并设为应用 UID/GID 1000、0700，拒绝符号链接，不修改已有日志。上线验收发现应用不能在 root 维护根目录下直接建子目录，因此补齐该初始化，并在新镜像验收中模拟实际权限。

## 验证

- Python 6 项独立测试：磁盘阻塞、50 并发提交 1,000 份诊断、队列溢出、写失败恢复、脱敏、版本作用域、关闭排空、提链成功/失败不受日志故障影响。
- 阻塞写入情况下，1,000 次投递实际 0.0389 秒；8 槽测试队列丢弃 992 份并正确计数，业务投递不等待磁盘。
- 11 项既有订阅集成测试通过：400 原单重试及单次结算、预算耗尽释放、设备重试、网络重试、未知错误、付款已提交不重放。使用本地 18983 专用临时库，真实上游全部模拟。
- Linux Go 全部 8 项测试通过，包括刷新成功/错误/空响应/身份不符与原凭据状态一致、Cookie 轮换、1000 次并发事件收集、CLI 两通道隔离和现有提链请求回归。
- Linux 基准：模拟 30 条事件收集与编码每轮约 0.413 毫秒，不代表实际整单上游耗时。未执行真实付费或订阅测试。
