# 代退目标团队会话等待与重试

2026-11-13，用户要求修复登录后未进入受邀团队却直接失败的订单，并推送 GitHub、更新正式环境。随后确认：登录完成后等待默认 5 秒，等待时间放入代退资源与调度的「调度与恢复」配置；仍失败时沿用现有原单重试。

## 已确认原因

两次提交使用相同母号和子号代理。第一次密码/MFA 及 Session 请求成功，但工作空间观察结果为 missing，没有执行目标团队选择，返回的会话未通过目标团队校验。原校验抛出普通 RuntimeError，导致 retryable 为 false、重试次数为 0，直接进入清理并释放冻结。第二次能读到目标团队，完成选择和办理。没有证据证明是代理网络故障，也无法断定邀请同步慢是唯一原因。

## 行为

- 子号密码/MFA 登录完成后，在继续回调、选择工作空间前等待。配置 `resource_recovery.post_login_wait_seconds`，默认 5 秒，可设 0～60 秒，0 不等待。开启或关闭办理前个人套餐观察均生效；每次重新登录都重新等待。
- 身份一致且有用户 ID，但凭据或 Session 未指向目标团队时，接入层抛出可重试 `team_session_not_ready`。必须继续通过原团队、邮箱和用户 ID 校验才可提交导出停用；身份不一致、身份缺失、坏凭据不归入此重试。
- 自动恢复开启时，由原队列按 `retry_seconds` 和 `recovery.max_retries` 重试；关闭时沿用进程内 `max_attempts`。原单重新登录、等待、进入对应团队，不直接重复使用已消费的回调。
- 原订单、母号、子号代理及冻结积分保持。此原因不触发代理冷却/切换，也不计入登录服务网络故障保护。成功按原条件只结算一次，耗尽后按原清理释放规则处理；已提交且结果未知时不重新提交。
- 新字段只在缺失时补默认值，不覆盖既有设置；后续启动保留运营保存的值。原 `merge_v2.py`、worker、钱包和重试调度不改，不重放现场历史订单。
