# 星桥与 GPT Register 完整整合

## 本次边界与修改地图

- `services/gpt-register/`：收纳 GPT Register 当前版本的运行代码、原管理台、用户交付和测试；注册引擎代码保持原样，仅修改平台接入与页面路径适配。
- `services/gpt-register/integration/`：星桥会话认证、身份映射、统一钱包事务和注册专用数据库迁移。
- `backend/registration_gateway.py`：同源注册入口，保留文件下载和流式响应，隔离注册服务故障。
- `frontend/src/`：采用下述最终导航；注册交付页面同源嵌入，去除重复菜单并自动适配页面高度。
- `scripts/registration_*.py`、`compose.registration.yml`：历史数据迁移、源码完整性检查、独立注册 app / worker 部署。
- `tests/`：并发余额争用、重复结算、交付回滚、权限、路径代理和迁移验证。

## 数据与执行边界

星桥 `users`、`sessions`、`ledger` 是统一身份、会话和钱包的权威来源。注册保留 `platform_*` 订单、队列、交付、供应商和配置表，通过显式身份映射关联星桥用户。历史注册用户、订单 ID 和加密数据不改写。

注册和订阅共用 PostgreSQL 事务能力，但使用各自表、队列锁、配置、代理资源和执行进程。注册引擎只在独立 worker 中运行；星桥调度器不领取注册任务。

状态流转：用户下单 → 同事务冻结积分并生成注册订单 → 原注册执行器处理 → 凭据完整交付与扣费同事务提交；失败／取消 → 仅释放该注册订单剩余冻结。重复回调通过唯一流水和订单项状态幂等处理。每个账号独立结算，部分成功只收成功交付部分。

GPT Register 1 积分对应星桥 100 个最小记账单位。迁移原可用和冻结余额时只入账一次，不以历史余额覆盖星桥余额，不重复重放历史业务流水。

注册运营中的账号注册／登录设置不再独立生效，共用功能开关读取星桥配置。原注册的业务定价、接单、并发、任务领取、代理与供应商设置保持独立。原管理台仍走 GPT Register 的管理员鉴权和内部 worker 代理，未经登录或非管理员不能访问。

注册办理已接入统一会员服务费减免，右侧显示会员与报价明细。资金中心按业务显示不同字段，注册流水不显示银行卡费用。两位小数计价、冻结结算、历史兼容及验证详见 [registration-membership.md](registration-membership.md)。

## 兼容与结算

- 注册用户按邮箱映射到星桥；已有星桥密码和身份不被覆盖，新迁入用户兼容原 scrypt 密码。原注册会话不作为新登录凭据。
- 历史注册订单、账号、加密凭据、兑换码、API Key、审计、财务、供应商成本和代理会话表完整迁入。历史 gr_ 密钥保持原权限，撤销或统一账户改密后失效。
- 历史流水仅投影显示，不重新入账。资金中心明确标注迁移前注册账户的余额快照；迁移入账与迁移后流水使用统一余额。重复迁移不会再次增加余额。
- 邀请规则统一读取星桥配置，新订单下单时快照。历史注册奖励保留原归属；同邮箱用户原邀请关系发生冲突时，不把历史奖励转给另一位邀请人。注册奖励沿用原平台的整积分取整，订阅保留原最小单位规则。
- 每单有独立冻结记录。交付凭据、订单项、注册流水和统一流水同事务提交；失败全回滚。注册不能释放订阅冻结，账户人工扣减也不能动用冻结积分。
- 统一 API 中订阅继续使用 `/api/v1/`，注册使用 `/registration/open/v1/`。注册返回积分，星桥返回最小单位，100 最小单位 = 1 积分。旧注册后台接口保留业务兼容，用户账户操作统一进入星桥。

## 首次正式整合步骤

以下为待执行步骤，不是已上线记录。

1. 用户提交并推送后，在 `/opt/1panel/apps/xufupython` 拉取指定 GitHub 版本。核对当前正式 Compose project、服务、数据库卷、5496 映射和镜像版本。仅新增 `compose.registration.yml` 叠加层，不替换现有正式 Compose、`.env` 或主密钥。新增至少 32 字符的独立 `REGISTRATION_GATEWAY_SECRET` 并妥善保存。
2. 预构建星桥 app 和 registration-app 两个镜像。以正式 Compose 加叠加层验证 `config`，注册 app / worker 不映射任何宿主机端口。首次新增服务共用星桥 PostgreSQL 内的独立注册表；不重建 PostgreSQL。
3. 先保存旧 gptreg 接单／领取开关初始值，关闭新接单，等待已受理任务自然完成，再关闭领取。确认订单项和代理绑定无在途，停旧 `gptreg-app` / `gptreg-worker`，保留 `gptreg-postgres`。同时检查星桥付款／续费任务，按既有流程取得维护窗口。
4. 在 `/opt/1panel/apps/codex-release-backups/` 为两项目备份并验证数据库、正式 Compose、`.env`、注册 `.runtime`、主密钥及镜像版本。备份期间旧注册引擎必须已停止，避免运行目录与数据库快照不一致。
5. 使用预构建星桥镜像仅执行 `backend.db.initialize()` 完成增量账本字段；使用注册镜像执行 `node integration/initialize.js` 创建注册表和统一接入函数。两条命令都不启动应用调度器或注册 worker，也不创建新的注册运行密钥。
6. 将旧注册 runtime 只读挂载为迁移源，星桥 `.registration-runtime` 挂载为目标。迁移进程需要同时连通现场核对后的两独立数据库网络；通过进程环境传入 `GPTREG_SOURCE_DATABASE_URL` 与 `DATABASE_URL`，不要将凭据写入命令日志。以有权读取源及写入目标的临时迁移容器执行：

   ```bash
   python scripts/registration_migrate.py --source-runtime /migration/source-runtime --target-runtime /migration/target-runtime
   ```

   来源与目标都校验队列锁，逐表 COPY 后核对行数和哈希，余额映射、邀请关系与历史密钥绑定在同一事务内；提交前再次验证两份 runtime 哈希。已有不同目标 runtime 拒绝覆盖。完成后把目标运行目录递归所有者设为注册镜像 UID/GID **1000:1000**，目录 0700、文件 0600；禁止调整源运行目录或其他服务卷权限。
7. 保持注册接单／领取关闭，使用既有正式 Compose 加叠加层、`--no-deps --no-build --force-recreate` 仅切换星桥 app 并启动新的 registration-app / registration-worker。验证 5496、星桥 `/health/live` 与 `/health/ready`、内部注册健康、登录、订单数、钱包对账、历史凭据解密、配置／密钥哈希、后台权限及未改动其他容器。
8. 只在以上核对成功后恢复原先保存的注册接单／领取开关。旧注册 app / worker 保持停止，避免新旧两套注册执行器使用同一供应商配置。后续启动须持续使用叠加层；注册镜像和 `.registration-runtime` 是该项目的正式依赖。
9. 尚未恢复新业务时可以回退应用镜像并保持注册关闭；一旦产生新订单／流水，不得以旧数据库备份覆盖新业务数据，也不得直接重开旧注册 worker。先停新接单、完成对账后制定数据兼容回退。成功验收后才按每项目最近 3 份规则清理旧发布备份。
